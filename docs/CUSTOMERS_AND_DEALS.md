# Customers and draft deals

Vehicle cover images and shared customer/deal list filters are supplied by the inventory and core modules. See [photos and filters](PHOTOS_AND_FILTERS.md) for the current full-suite verification and storage controls.

Implemented October 23, 2026 for synthetic development data.

Customer is the shared identity/contact record within a dealership. DraftDeal holds protected references to inventory.Vehicle, customers.Customer as buyer, and an optional co-buyer. Do not create separate sales and BHPH copies of a person. A later servicing account should reference the approved deal/contract and the same customer IDs. Contract-party snapshots must be preserved separately at finalization; a current address/contact profile is not a substitute for historical contract evidence.

Core access helpers enforce membership and owner/staff editing consistently. Viewer accounts can read only their dealership's records. Form querysets are scoped server-side; model validation also checks same-dealership references. Direct SQL and unvalidated ORM writes are not supported public interfaces. Customer and deal saves record actor and version history in dedicated, protected event relations. These records are not tamper-proof against a database administrator.

Adding a customer requires first/last name, with optional phone/email. Matching names or normalized contact details produce a dealer-scoped warning. Users can open matches, explicitly confirm a distinct person, or select Use this customer during inline deal entry. Shared phone numbers and names are not forced unique. No automatic merges; simultaneous creates can still produce duplicates.

Customer selection labels include contact details and a customer number to distinguish people with the same name. A dealership with no customers opens the inline new-customer path automatically. Customer search requires all name/email words or matches a normalized phone number; its query interface belongs to `customers.queries` and is reused by the deals module. Draft search covers buyers/co-buyers, contact details, vehicle words/year, stock number, VIN, and draft number. A leading `#` requests an exact draft number. Both lists paginate through all matching dealer-scoped records, 25 per page, and preserve the search when changing pages.

Existing customer selections and an inline new-customer path share one deal form. Customer and vehicle profiles link directly to starting a draft, with the selected record prefilled only when it belongs to the active dealership and the vehicle is not sold. Invalid deal input creates no customer. Customer, draft, and both change records commit together; an audit failure rolls everything back. Revision tokens detect stale customer/deal edits under PostgreSQL row locks. Multiple drafts for a vehicle are allowed and do not reserve inventory.

Each new-draft form carries a creation UUID. A database constraint makes it unique within the dealership. Repeating a successful create submission opens the original draft without applying the repeated payload. A concurrent collision rolls back the losing inline customer and audit records before opening the saved draft. This prevents duplicates from retries of one form; separate new forms or standalone customer creates can still create matching identities. Editing a saved draft continues to use revision checks. Migration `deals.0002` backfills a different UUID for every existing draft before enforcing the constraint; it preserves existing IDs and worksheet amounts.

Draft fields are worksheets, not financing contracts: sale price, manually entered tax/title/registration/dealer fees, trade allowance/payoff, planned down payment, notes. Vehicle and buyer are the first required choices; optional worksheet amounts are initially collapsed and automatically reopen if they contain saved values or validation errors. Decimal arithmetic produces a draft balance. Negative amounts/balances are rejected. No rates, APR, charge limits, taxes or legal disclosures are inferred. A planned down payment is not a receipt; no loan, ledger posting, payment, signature, or sold status is created. Each save records an actor, timestamp, revision, and draft snapshot; the detail page shows recent save history. Production lending/document rules remain gated under the product plan.

The deal page is a connected deal desk: compact vehicle/buyer/co-buyer context, a toolbar with Save, a deal-structure column, and a shared summary. Structure, Notes, and History are real sections with keyboard-operated tab navigation; the selected section is preserved after saving. Changing sections keeps entered work. Invalid fields in hidden sections are revealed before focus/validation, and a no-JavaScript fallback displays all sections. The vehicle's structured title brand remains visible. Server calculations share one Decimal-based function; browser previews use integer cents, including the net trade adjustment. The summary omits unused zero-value fee/trade lines. Worksheet saves can change only amounts/notes, use the same revision protection as the party editor, and share the atomic save/audit service. Unchanged submissions create no new revision. Conflicts keep the entered work and link to the latest saved deal in another tab. Viewer fields are disabled and server-side writes are denied.
