# Railet MFA design — research and implementation backlog

Source check: November 7, 2026. **Status:** an offline, synthetic-only encryption and TOTP experiment exists with synthetic factor/event persistence; no login integration, MFA routes, real enrollment or live behavior is enabled. Decisions below are proposals, not approved security controls, legal advice, a compliance determination, or a claim of NIST certification. Recheck primary sources, versions, advisories and applicable law before implementation and launch. Production deployment and real customer data remain separately gated. Essential MFA must be in the Community edition, including self-hosted deployments.

## Existing access paths and constraints

- `railet/urls.py` mounts Django's `LoginView` and `LogoutView` at `/accounts/login/` and `/accounts/logout/`; `templates/registration/login.html` collects the standard credentials and CSRF token. No MFA library, MFA verification middleware or MFA routes are configured in `railet/settings.py` or `requirements.txt`.
- Django `AuthenticationMiddleware` and session middleware establish the authenticated user. `core.access.member_view` wraps `login_required`, resolves the user's `Membership`, and sets `request.member`. `require_editor` checks owner/staff; viewer is read-only where individual views enforce it. The membership is currently one-to-one with a user and points to a dealership. Do not treat a role check or `is_authenticated` as proof of a verified second factor.
- Private document/packet downloads, customer and account exports, inventory images and financial screens are separate routes; many are `@member_view` protected. Scope checks in those views/services still matter after MFA. Audit all URL patterns, redirect/confirm/download endpoints, internal services and any future API, admin, SSO, static/media or alternative login paths rather than assuming decorators cover everything.
- Settings configure HttpOnly sessions, secure session/CSRF cookies and HTTPS redirect when `DEBUG` is false, and staging configures a proxy header. They do not establish a complete production transport, proxy trust, session lifetime, MFA or rate-limiting policy. Development demo flags are tied to `DEBUG`; neither those gates nor a successful login makes this build ready for customer data.
- There is currently no user-facing password-reset route in the inspected URL configuration. A future reset flow, Django admin, shell-created accounts and service integrations must not become bypasses. Django's default session backend is in use; this design must not assume an existing user-to-session index or global revocation mechanism.

## Proposed architecture and policy

### 1. Enrollment and authentication

1. Require a distinct individual account for each worker; no shared staff credentials. An owner provisions an account and establishes its dealership/role; a new user receives a **single-use, short-lived, rate-limited** enrollment invitation through a separately verified channel. The invitation grants only an enrollment flow, never workspace access. Do not display secrets in links, logs, analytics or notifications. How an operator initially verifies identity and delivers invitations is an open deployment decision.
2. After password verification, keep the browser in a **pre-authentication** state with a short-lived, server-side, one-use challenge bound to that browser/session, user, dealership, purpose and expiry. Do not create a full workspace session. The only pre-auth routes are explicitly enumerated login, MFA challenge, safe logout and authorized enrollment/recovery endpoints; never permit exports, private files or business APIs.
3. Offer WebAuthn security keys/passkeys as the preferred phishing-resistant choice and a password-plus-TOTP authenticator as an accessible fallback. Verify WebAuthn RP ID, allowed origin, cryptographic challenge, type, credential ownership and flags using a reviewed library; enforce user verification when claiming a multifactor passkey, distinguish single-factor security keys, and test actual browser/OS support. Do not claim every passkey is automatically MFA or AAL2. Choose whether WebAuthn is second factor to a password or an explicitly verified multifactor authenticator, and validate that decision independently. RP ID/origin changes require a migration and recovery plan for each self-hoster.
4. Enroll TOTP only in the restricted enrollment flow or after recent verified MFA. Generate a unique strong random seed; show its QR and a screen-reader-readable manual key once over HTTPS with `Cache-Control: no-store`. Confirm possession with a valid code before binding it. Expire unconfirmed enrollment and provide an accessible alternative. Never email/SMS the seed, use real customer information as an issuer label, or save QR/seed in analytics, support reports or ordinary exports.
5. On successful second-factor verification, atomically consume the challenge, rotate the session identifier and CSRF token as appropriate, and create a fresh verified session. Bind its server-side assurance record to user ID, dealership ID, authentication time, factor/method, security epoch and current session identity; never place an OTP seed or recovery code in a session. Keep any redirect target local and allowlisted. Full authentication must not be inherited from a different user or earlier browser login.

### 2. Enforcement and sessions

- Implement a centrally enforced, fail-closed server-side MFA boundary after Django authentication and before business handlers, using a small explicit route allowlist for login, challenge, enrollment, recovery and logout. Reject unverified or stale sessions for **every** protected response and mutation, including GET/HEAD exports, document artifacts and image downloads. Middleware ordering and exception behavior must be tested, not inferred. Map all routes and provide an explicit machine-to-machine identity design before any future API or background integration; do not allow API keys or Django admin to skip the boundary.
- On each protected request, validate an active user, active membership, the current dealership/role, current assurance/session epoch and factor status server-side. The current membership model has no active field: implementation must define and enforce how suspension/deletion/revocation is represented. MFA augments, never replaces, per-record dealership isolation and authorization; a verified viewer remains a viewer. `Membership` currently binds one dealership; any future multi-dealership selection needs explicit reauthorization and tests.
- A server-side per-user security epoch/version increments transactionally on password reset/change, factor removal/replacement, recovery, account suspension and membership/role changes. Each protected request compares it to the verified session; stale sessions cannot regain assurance. Implement per-session revocation and an auditable owner/user session list without storing raw session tokens. On logout invalidate that session; a security incident or recovery revokes all relevant sessions and pending challenges. Review Django password-change semantics so a preserved session cannot accidentally bypass MFA.
- Proposed starting limits for risk review: require fresh full authentication at most every 24 hours and reauthentication after one hour of inactivity, with accessible advance notice and saved-work behavior. These are **design candidates** informed by NIST's AAL2 recommendations, not claims of compliance or a final policy. Define activity, monotonic/UTC clock behavior, multi-tab concurrency, timezone independence and what resets each timer; never extend indefinitely via background polling. Do not use persistent 'remember this device' cookies as a substitute for MFA. Apply recent MFA step-up to factor changes, recovery-code regeneration, membership/role changes and sensitive exports; bind the step-up to the operation and reject stale previews after reauthentication.
- Require HTTPS and authenticated origin end to end, strict trusted-host/proxy configuration, Secure/HttpOnly/SameSite cookies, CSRF, session-ID rotation, clickjacking protection and no credential caching. Session cookies are bearer secrets: these measures do not by themselves provide cryptographic device binding or eliminate session theft. Establish TLS/HSTS, reverse-proxy boundaries and key management through a deployment review, not assumptions about the developer VM.

### 3. Secrets, keys, recovery and revocation

- **TOTP seeds must be decryptable for verification**, so password hashing is inappropriate. Use a reviewed authenticated-encryption implementation with per-record nonce, versioned key identifier and associated data binding the ciphertext to its tenant, user, factor and purpose. Store encryption keys outside the application database and database backups, separate from Django `SECRET_KEY`, with least-privilege runtime access. An external KMS/HSM is one option; a self-hosted secret manager or protected key file is another, still requiring a documented threat model and operator controls. Never invent encryption primitives or expose keys through exports, logs or debug pages.
- Select and document an envelope-encryption/key-provider interface, provisioning, rotation with old-key decrypt/new-key encrypt, backup, restore, break-glass and key-loss behavior. Back up encrypted seed data and key material **separately** and test a clean restore, access revocation and rotation without silently dropping users. Fail closed if the key is unavailable or authentication fails; never fall back to plaintext or disable MFA. Whether an old encrypted backup contains an earlier seed and how factor revocation survives restore are explicit recovery risks requiring a reviewed runbook.
- Generate high-entropy, independently random **one-time recovery codes**, display once, store only salted one-way verifiers, and atomically mark each consumed. Define a separate pepper/key only if needed and backed up appropriately. A recovery code is an alternative second factor **after password or equivalent approved first factor**, not a password reset or unconditional login. Regeneration requires recent MFA and invalidates previous codes atomically. Verify actual package storage against this design; implement a reviewed adapter or reject the package if it cannot meet it.
- Support registering at least two independent authenticators, with clear names and dates and easy revocation; do not rely exclusively on one phone, SMS, email or a single synced account. After use of a recovery code, show how many remain and encourage adding a replacement factor. Send a security notification through an independently verified channel if configured, without revealing codes or customer information. A notification is not identity proof.
- Lost-all-factors recovery must not be a helpdesk password-only reset. Use a documented, separately verified identity procedure and approval by authorized dealership administrators, audit the request and approval, invalidate old factors/challenges/sessions, then issue a restricted single-use enrollment grant. Define a secure two-person process where feasible and an offline, auditable bootstrap/break-glass process for a one-owner dealership or lost encryption key; do not require a nonexistent second owner or introduce an unaudited universal bypass. Recovery channel, proof, delay/notification and emergency access controls require security and legal review. Ephyro has no automatic access to self-hosted data.

### 4. Abuse, replay, concurrency and audit

- Rate-limit password attempts, MFA attempts, recovery and enrollment independently by account and risk-appropriate source/device signals, including unknown accounts. Use atomic counters in a shared durable store suitable for multi-worker/multi-node deployments, handle trusted proxies correctly, use generic failure messages, bounded backoff and support safe recovery without allowing easy targeted denial of service. Define thresholds after testing; on limiter/store failure deny sensitive operations rather than bypassing. Do not key limits only by IP or trust unvalidated forwarded headers.
- For TOTP, check the accepted timestep/window and persist a per-device last accepted step **atomically** so the same OTP cannot succeed in concurrent requests or in alternate textual encodings. Strictly normalize/validate input, compare safely and account for clock skew; prevent a previously accepted code from being accepted again while it remains valid, including the rare case of collisions across allowed timesteps, without retaining the plaintext code. Rate-limit and alert on repeated errors. Every WebAuthn challenge is cryptographically random, scoped, expires and is consumed once; validate origin, RP ID and flags. Review sign-counter behavior for synced/multi-device passkeys; counters are signals, not an unconditional clone verdict. Recovery-code consumption, enrollment confirmation, revocation and factor replacement must also be atomic and idempotent.
- Establish a consistent lock order for user security state, factor/challenge and session metadata; use database transactions/unique constraints and row locks or equivalent conditional updates. Concurrent login and revocation must never issue a usable session from a revoked factor or stale epoch. Confirm behavior under PostgreSQL using separate connections and barriers; SQLite is useful for functional tests but is not evidence of PostgreSQL concurrency guarantees.
- Append a privacy-minimized security audit for enrollment, verification failure/success, rate limiting, recovery, factor changes, revocation and administrative approval. Record actor/subject IDs, dealership, factor type, action/outcome, UTC time and correlation ID as appropriate; never log passwords, QR payloads, seeds, OTPs, recovery codes, cookies, private keys or access tokens. Log/audit failure handling, retention, alerting, notification delivery and operator access need a reviewed policy; protect logs from tampering and verify tenant isolation.

## Staged implementation and acceptance gates

1. **Threat model and decisions:** enumerate users, protected endpoints, service identities and deployment topologies; choose a reviewed library and key provider, RP IDs/origins, timeout and lockout policy, audit approach, enrollment identity proof and one-owner recovery. Have the Qualified Individual and qualified counsel evaluate applicability, with written operational ownership. No live rollout.
2. **Synthetic, isolated prototype:** use invented users, fake factors and local-only secrets; implement the core Community MFA boundary, enrollment/challenge, one-time recovery codes and fail-closed session/epoch behavior behind an explicitly development-only gate. No outbound communications, live account migration or hidden MFA bypass. Validate license/SBOM and dependency patch status. A prototype cannot be used with customer data.
3. **Security and usability verification:** exercise direct/alternative login, private file/export GET/HEAD and cross-dealer access; owner/staff/viewer changes and revocation; expired/tampered/cross-user challenges and redirects; stolen or rotated sessions; password reset; WebAuthn wrong origin/RP/challenge/user verification; TOTP skew, leading zeros, replay and concurrent reuse; atomic recovery-code races; concurrent revoke/login; limiter evasion and outage; encryption tamper/key loss/rotation and separate-key restore. Run SQLite functional tests and PostgreSQL multi-connection race tests. Test keyboard, screen-reader labels/errors, high contrast, no-phone flow and real staff workflows using invented records. Independent security review and an incident/recovery drill remain required.
4. **Migration and deployment plan:** inventory existing accounts and sessions, schedule supervised enrollment, establish separately verified bootstrap and recovery, protect access during transition, test rollback without creating password-only access, and revoke or reverify existing sessions at cutover. Approve monitoring, support, key custody, TLS and restore runbooks. Disable alternate login paths and check actual infrastructure. No production rollout, real data or change to gates without the owner's explicit authorization and required reviews.

## Implemented synthetic encryption foundation (November 7, 2026)

`core/mfa_secrets.py` is a standalone experiment, not an MFA feature or production key provider. It uses [PyCA cryptography AES-GCM](https://cryptography.io/en/stable/hazmat/primitives/aead/) with a random 96-bit nonce per operation, a 256-bit explicitly supplied key, and authenticated canonical context including format version, key ID, dealership, user and factor. The return value is a versioned dictionary containing only encoded nonce, ciphertext and key ID; the caller supplies the exact context on decryption. The service performs no database writes, key generation, logging, exports, authorization, login or network requests. It is not proof of broader encryption, legal compliance or readiness for real credentials.

**All calls require** Django `DEBUG=True`, environment variable `RAILET_DEV_MFA_SYNTHETIC=1`, `RAILET_DEV_MFA_ACTIVE_KEY` naming an entry, and `RAILET_DEV_MFA_KEYS` containing a JSON object of distinct key IDs to canonical URL-safe base64-encoded 32-byte keys. All identifiers must use `synthetic-` prefixes and the bytes must start with `synthetic:` and contain at least one additional byte. These labels and the DEBUG/opt-in gates reduce accidental use; they **cannot prove data or identities are invented**, nor make a debug deployment safe for real users. Use invented values only. There is no default key, automatic environment loading, real-factor support or fallback to Django's `SECRET_KEY`.

Keep even development keys out of source, commits, ordinary exports, logs, issue reports and shared databases. The process environment is readable by the process and may be exposed by diagnostics, crash reports, subprocesses or host administrators; it is an experiment-only configuration, not an approved production key-management design. Errors do not intentionally include secrets, but tools that capture local variables can disclose them. AAD is authenticated, not encrypted, and is supplied by the caller rather than stored in the envelope. Record identifiers must not contain personal information.

To rehearse rotation, explicitly configure old and new distinct keys, select the new active key ID, and call `rotate_synthetic_secret` with the original authenticated context; it decrypts with the envelope's key ID and re-encrypts with the active key and a fresh nonce. Keep the old key until every needed synthetic envelope is migrated and verified. Removing it early makes old records unavailable. This pure helper does **not** atomically persist rotated results or prevent concurrent writes: any future persistence layer must use a transaction and compare-and-swap/version checks, and test rollback, restore and key-revocation procedures. AES-GCM nonces must never repeat for the same key; random 96-bit nonces have a nonzero collision probability, so this development experiment is not a substitute for a production nonce/key-volume policy.

The dependency installed and checked in the project virtual environment is `cryptography==50.0.2` (Apache-2.0 OR BSD-3-Clause), with cffi 2.1.1 (MIT-0) and pycparser 3.12 (BSD-3-Clause); see [third-party notices](../THIRD_PARTY_NOTICES.md). Those exact artifacts were observed for this environment, while `requirements.txt` uses a supported range. Redistributed wheels can include OpenSSL and other native components with separate notices; review resolved artifacts and maintain advisories, a lock/SBOM and supply-chain controls before any release. The encryption foundation does not select a production MFA authentication package.

Focused tests use invented keys/bytes and cover nonce variation, tampering, context isolation, missing/malformed keys, version and key-ID changes, rotation, no intentional logging, and DEBUG/explicit-opt-in gates. They do not establish cryptographic review, zeroization, production resilience, operational recovery, or integration with actual factors and user sessions. Other MFA tasks and all production gates remain open.

## Offline synthetic TOTP experiment

`core/mfa_prototype.py` uses the [django-otp](https://pypi.org/project/django-otp/) 1.7.5 TOTP primitive (Unlicense; the maintainer describes it as stable and maintained with limited ongoing investment). This is a library selection only for the experiment, not endorsement for production. The dependency is pinned in `requirements.txt`; verify advisories, artifacts, licenses and an SBOM before release.

The service requires the encryption helper's DEBUG, explicit environment opt-in, valid separate key and `synthetic-` context gates for every operation. It creates an invented 20-byte random seed inside the AES-GCM envelope; it has no relationship to Django users or dealership records and exposes no QR, endpoint or login integration. Synthetic labels cannot prove a caller supplied invented data. A six-digit token is checked with a 30-second period, one-step clock tolerance and a minimum step after the last accepted step. Five rejected attempts lock that factor for 60 seconds. PostgreSQL row locks serialize verification and a transaction records minimal enrollment/accept/reject events while atomically advancing replay or throttle state. Update/delete guards protect event rows on SQLite and PostgreSQL; database administrators and table rebuilds remain outside that guarantee. Locked retries are not written as events to avoid unbounded history. SQLite has no row-level lock and is supported only for single-worker experimentation; database lock errors fail closed.

**Collision handling:** Six displayed digits can coincide at different time steps. On acceptance the prototype uses the library to inspect subsequent steps whose one-step-skew validity windows touch and atomically consumes the entire connected run of matching steps, without storing the displayed token. A bounded 128-step scan rejects and counts the attempt toward throttling if the run cannot be resolved. A collision can temporarily block a different legitimate code in an intervening step; this is a deliberate fail-closed tradeoff for this experiment. If a code disappears from the permitted window and later independently recurs, that is a new validity interval. The audit stores an `enrolled-v2` marker for new synthetic factors; factors enrolled by the previous implementation are denied because their earlier consumption cannot be reconstructed. Start fresh with a different synthetic factor ID. Stop all old workers before testing this version: an older process does not enforce the new marker or collision rule. This prototype and its database-admin trust boundary still need independent security review before any live use.

Limitations: no possession confirmation, authentication session, actual pre-auth challenge, recovery, phishing-resistant factor, distributed source-level limits, production authorization, deployment key management, clock monitoring, secure erasure or UX exists. django-otp's primitive and these prototype limits have not had an independent security review. This is not protection for real users, compliance evidence or a release decision. Baseline MFA and all live-production gates remain open.
